# 0.3 Glosarium Istilah Teknis

Halaman ini adalah kamus rujukan cepat untuk seluruh istilah teknis yang digunakan dalam dokumentasi sistem RAG. Setiap istilah dijelaskan dalam bahasa sederhana.

> **Tips:** Gunakan `Ctrl+F` untuk mencari istilah yang Anda temui di halaman lain.

---

## Apa yang Akan Anda Pelajari

- Memahami ~30 istilah teknis utama dalam ekosistem RAG dan LLM
- Mengetahui hubungan antar konsep
- Referensi cepat yang bisa dirujuk kapan saja

## A — E

### API (Application Programming Interface)
Jembatan komunikasi antar program komputer. Dalam sistem ini, Gateway dan Worker berkomunikasi melalui API — Gateway mengirim permintaan HTTP ke Worker, dan Worker membalas dengan data.

### API Key
Kunci rahasia berupa teks panjang yang digunakan untuk membuktikan identitas pemanggil API. Sistem ini menggunakan dua API key: `GOOGLE_API_KEY` (untuk Gemini) dan `INTERNAL_API_KEY` (untuk komunikasi Gateway ↔ Worker).

### Bi-Encoder
Model embedding yang memproses pertanyaan dan dokumen **secara terpisah** lalu membandingkan vektor hasilnya. Cepat, tapi kurang teliti dibanding Cross-Encoder. Digunakan di tahap pertama pencarian (BGE-M3). Lihat: [Embedding BGE-M3](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.4-embedding-bge-m3.md).

### Chunk / Chunking
Proses memecah dokumen panjang menjadi potongan-potongan kecil agar muat dalam kapasitas LLM dan bisa dicari secara presisi. Sistem ini menggunakan "Schema v2" dengan 4 tipe chunk: `text`, `figure`, `table_parent`, `table_anchor`. Lihat: [Chunking Schema v2](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.2-chunking-schema.md).

### Citation / Sitasi
Penanda sumber dalam jawaban, seperti `[S1]`, `[S2]`. Setiap klaim dalam jawaban RAG harus merujuk ke sumber yang nyata. Sistem ini memiliki validasi dan perbaikan otomatis untuk sitasi. Lihat: [Citation Validation](../01-Komponen-Teknis/1.3-Alat-Generation/1.3.2-citation-validation.md).

### Context Window
Batas maksimum teks yang bisa dibaca LLM dalam satu kali proses. Ibarat "daya ingat jangka pendek" AI — semua pertanyaan, konteks dokumen, dan instruksi harus muat dalam jendela ini. Gemini 2.5 Flash memiliki context window ~1 juta token.

### Cosine Similarity
Rumus matematika untuk mengukur kemiripan dua vektor. Nilai 1.0 = identik, 0.0 = tidak berhubungan sama sekali. Digunakan oleh Qdrant untuk mencari dokumen yang paling mirip dengan pertanyaan.

### Cross-Encoder
Model yang membaca pertanyaan dan dokumen **bersama-sama** untuk menilai relevansi. Lebih teliti dari Bi-Encoder, tapi jauh lebih lambat. Digunakan di tahap reranking (BGE-reranker-base). Lihat: [Cross-Encoder Reranker](../01-Komponen-Teknis/1.2-Alat-Retrieval/1.2.3-reranker-cross-encoder.md).

### Dense Vector
Representasi teks dalam bentuk deretan angka desimal padat (misal: 1024 angka). Menangkap **makna semantik** — kalimat yang artinya mirip akan memiliki vektor yang berdekatan, meskipun kata-katanya berbeda.

### Docker
Platform untuk menjalankan aplikasi dalam "kontainer" terisolasi. Sistem ini menggunakan Docker untuk menjalankan Qdrant.

### Docling
Parser PDF buatan IBM yang menggunakan Vision-Language Model untuk memahami struktur dokumen (judul, paragraf, tabel, gambar) dan mengubahnya menjadi Markdown terstruktur. Lihat: [Parser Docling](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.1-parser-docling.md).

### Embedding
Proses mengubah teks menjadi vektor (deretan angka) agar mesin bisa mengukur kemiripan makna. Model BGE-M3 menghasilkan Dense Vector (1024 dimensi) + Sparse Vector sekaligus. Lihat: [Embedding BGE-M3](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.4-embedding-bge-m3.md).

## F — L

### FastAPI
Framework Python untuk membuat API web dengan performa tinggi. Worker RAG menggunakan FastAPI sebagai server HTTP.

### Fusion (RRF)
Teknik menggabungkan hasil dari beberapa pencarian berbeda menjadi satu ranking terpadu. Reciprocal Rank Fusion (RRF) memberi skor tinggi pada dokumen yang muncul di posisi atas dari **banyak** pencarian sekaligus. Lihat: [Orchestrator & RRF Fusion](../01-Komponen-Teknis/1.2-Alat-Retrieval/1.2.2-orchestrator-dan-fusion.md).

### Gateway
Service .NET (ASP.NET Core) yang menjadi pintu masuk utama sistem. Menangani chat orchestration, query routing, validasi sitasi, dan document management. Berjalan di port 8080.

### gRPC
Protokol komunikasi berkecepatan tinggi (lebih cepat dari HTTP biasa). Gateway berkomunikasi dengan Qdrant menggunakan gRPC untuk operasi dokumen.

### Hallucination / Halusinasi
Ketika LLM mengarang jawaban yang terdengar meyakinkan tapi tidak berdasarkan fakta. Ini adalah masalah utama yang RAG dan Citation Validation berusaha atasi.

### Hybrid Search
Kombinasi dua metode pencarian sekaligus: Dense (semantic/makna) + Sparse (keyword/kata kunci). Menghasilkan hasil yang lebih akurat dibanding masing-masing metode sendiri. Qdrant mendukung hybrid search secara native.

### Ingestion
Proses memasukkan dokumen ke dalam sistem: Parse PDF → Potong (Chunk) → Ubah ke Vektor (Embed) → Simpan di Database. Ini dilakukan **sebelum** ada yang bertanya, ibarat "pustakawan menata buku di rak."

### Intent Classification
Proses mengklasifikasikan niat pengguna dari pertanyaannya. Query Router mengklasifikasikan ke 4 kategori: SEARCH, SUMMARIZATION, CHIT_CHAT, AMBIGUOUS.

### LLM (Large Language Model)
Model AI berskala besar yang dilatih dengan miliaran teks untuk memahami dan menghasilkan bahasa manusia. Contoh: GPT-4, Gemini, Claude. Lihat: [Konsep Dasar LLM](0.1-konsep-dasar-llm.md).

## M — R

### Metadata
Informasi tambahan yang dilampirkan pada setiap chunk: nama file asal, nomor halaman, ID dokumen, tipe chunk, dll. Metadata memungkinkan sistem melacak asal-usul setiap jawaban.

### Multi-Agent Pipeline
Arsitektur di mana beberapa agen LLM dengan spesialisasi berbeda bekerja sama secara berurutan. Sistem ini menggunakan 3 agen: Query Router, Chit-Chat, dan Grounded Answer. Lihat: [Multi-Agent Pipeline](../01-Komponen-Teknis/1.3-Alat-Generation/1.3.1-multi-agent-pipeline.md).

### OCR (Optical Character Recognition)
Teknologi untuk membaca teks dari gambar/scan dokumen. Docling mendukung OCR untuk dokumen yang di-scan.

### Overlap
Jumlah teks yang tumpang-tindih antar chunk berturutan. Overlap 200 token berarti 200 token terakhir chunk sebelumnya diulangi di awal chunk berikutnya, menjaga kesinambungan konteks.

### Prompt
Instruksi yang diberikan kepada LLM. System Prompt mengatur perilaku agen (misal: "Jawab hanya berdasarkan konteks, jangan mengarang"). User Prompt berisi pertanyaan aktual dan konteks dokumen.

### Provider
Penyedia layanan LLM (Google Gemini, OpenAI, Ollama, dll). Sistem ini bersifat provider-agnostic — bisa diubah tanpa mengubah kode.

### Qdrant
Database vektor open-source yang ditulis dalam Rust. Menyimpan dan mencari vektor dengan kecepatan tinggi, mendukung hybrid search (Dense + Sparse) secara native. Lihat: [Database Qdrant](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.5-database-qdrant.md).

### Query Router
Agen LLM pertama yang mencegat setiap pertanyaan dan mengklasifikasikan niat pengguna. Menentukan apakah harus mencari di database (SEARCH), ngobrol biasa (CHIT_CHAT), atau minta klarifikasi (AMBIGUOUS). Lihat: [Intelligent Query Router](../01-Komponen-Teknis/1.2-Alat-Retrieval/1.2.1-intelligent-query-router.md).

### Query Rewrite
Proses memperbaiki/memperluas pertanyaan pengguna agar pencarian lebih efektif. Misal: "sanksi rokok" → "sanksi pelanggaran merokok bagi mahasiswa". Sistem ini menggunakan metode rule-based (cepat, gratis).

### RAG (Retrieval-Augmented Generation)
Teknik yang menggabungkan pencarian dokumen (Retrieval) dengan generasi teks AI (Generation). Alih-alih menjawab dari "ingatan", LLM diberi dokumen ref sebagai "contekan" untuk menjawab secara akurat. Lihat: [Konsep Dasar RAG](0.2-konsep-dasar-rag.md).

### Rate Limiting
Pembatasan jumlah permintaan API per satuan waktu. Melindungi dari tagihan berlebih dan server overload. Sistem mengizinkan maksimal 120 panggilan LLM per menit.

### Reranking
Proses menilai ulang hasil pencarian awal menggunakan model yang lebih teliti (Cross-Encoder). Memastikan hanya dokumen paling relevan yang digunakan untuk menjawab.

### Retrieval
Proses mencari potongan dokumen yang relevan dengan pertanyaan pengguna. Mencakup: embedding pertanyaan → hybrid search → RRF fusion → reranking → filtering.

### Retry
Mekanisme percobaan ulang otomatis saat API gagal (misal: server sibuk, error 429). Sistem mencoba ulang hingga 3 kali dengan jeda bertahap (exponential backoff).

## S — Z

### Schema v2
Strategi chunking canggih yang mengklasifikasikan chunk berdasarkan tipe konten (text, figure, table_parent, table_anchor) alih-alih memotong secara membabi-buta berdasarkan ukuran. Lihat: [Chunking Schema v2](../01-Komponen-Teknis/1.1-Alat-Ingestion/1.1.2-chunking-schema.md).

### Sparse Vector
Representasi teks di mana sebagian besar nilainya nol — hanya kata-kata yang benar-benar muncul memiliki skor. Mirip pencarian kata kunci tradisional (BM25), tapi dalam format vektor. Akurat untuk istilah teknis spesifik.

### SSE (Server-Sent Events)
Teknologi streaming di mana server mengirim data secara bertahap ke client. Digunakan di `/api/chat/stream` agar jawaban muncul token per token secara real-time, bukan menunggu jawaban lengkap.

### Streamlit
Framework Python untuk membuat aplikasi web interaktif dengan cepat. Digunakan sebagai antarmuka pengguna sistem RAG (upload PDF, chat, kelola dokumen).

### Temperature
Parameter yang mengatur tingkat kreativitas LLM. Nilai 0.0-0.3 = sangat fokus dan konsisten (cocok untuk fakta). Nilai 0.7-1.0 = lebih kreatif dan bervariasi (cocok untuk ngobrol).

### Timeout
Batas waktu maksimum untuk suatu proses sebelum dibatalkan paksa. Gateway memberi Worker timeout 600 detik. Agen LLM memiliki timeout 90 detik per panggilan.

### Token
Unit terkecil yang diproses LLM. Satu token ≈ ¾ kata bahasa Inggris, atau ≈ ½ kata bahasa Indonesia. Semua biaya LLM dihitung per token.

### Vector / Vektor
Deretan angka yang merepresentasikan teks dalam ruang matematika multi-dimensi. Teks dengan makna serupa akan memiliki vektor yang berdekatan. Fondasi dari pencarian semantik.

### Vector Database
Database yang dirancang khusus untuk menyimpan dan mencari vektor dengan kecepatan tinggi. Berbeda dari SQL database yang mencari berdasarkan kecocokan kata. Contoh: Qdrant, Pinecone, ChromaDB.

### Vision AI / VLM
Model AI yang bisa "melihat" dan memahami gambar, bukan hanya teks. Digunakan saat ingestion untuk mendeskripsikan chart, grafik, dan diagram dalam PDF agar bisa dicari secara tekstual.

### Worker
Service Python (FastAPI) yang menangani pekerjaan "berat" di sisi ML: parsing PDF, embedding, hybrid search, dan reranking. Berjalan di port 8000.
