## 1. Quick Chat Check dengan test_rag.py

### A. Tujuan

Script `worker/test_rag.py` adalah **quick smoke test** untuk memverifikasi bahwa pipeline RAG berfungsi end-to-end. Ia mengirim test query dan mencetak hasilnya, menggunakan **streaming** (SSE) terlebih dahulu, dan fallback ke non-streaming jika gagal.

### B. Prasyarat

1.  Qdrant harus berjalan (`docker compose up -d`)
2.  Worker harus berjalan di `localhost:8000`
3.  Gateway harus berjalan di `localhost:8080`
4.  Minimal satu dokumen harus sudah di-ingest

### C. Cara Menjalankan

```bash
cd worker
python3 test_rag.py
```

Default target: `http://localhost:8080/api` (Gateway). Bisa diubah dengan environment variable `RAG_API_URL`.

## 2. Evaluasi Kualitas dengan evaluate_rag.py

### A. Tujuan

Script `worker/evaluate_rag.py` adalah **quality evaluator** yang menjalankan serangkaian query dan mengukur berbagai metrik kualitas jawaban RAG.

### B. Metrik yang Diukur

| Metrik | Deskripsi |
|--------|-----------|
| **success_rate** | Persentase request yang berhasil (HTTP 200) |
| **citation_presence_rate** | Persentase jawaban yang mengandung sitasi `[S1]`, `[S2]`, dll |
| **citation_valid_rate** | Persentase sitasi yang valid (ID sesuai dengan sources) |
| **avg_source_count** | Rata-rata jumlah sumber per jawaban |
| **avg_grounding_overlap** | Rata-rata overlap token antara jawaban dan sumber |

### C. Cara Menjalankan

```bash
cd worker

# Default (target Gateway di localhost:8080)
python3 evaluate_rag.py

# Custom API base URL
python3 evaluate_rag.py --api-base http://localhost:8080/api

# Custom test cases
python3 evaluate_rag.py --cases ./my_eval_cases.json

# Save report
python3 evaluate_rag.py --out ./rag_eval_report.json
```

### D. Format Custom Test Cases

```json
[
    {"id": "q1", "question": "Apa fitur utama aplikasi?"},
    {"id": "q2", "question": "Model apa yang digunakan untuk deteksi?"},
    {"id": "q3", "question": "Bagaimana cara kerja tracking?"}
]
```

### E. Contoh Output

```
RAG Evaluation
================================================================================
q1       OK    citations=['S1', 'S2'] sources=5 grounding=0.72
q2       OK    citations=['S1', 'S3'] sources=5 grounding=0.65
q3       OK    citations=['S2']       sources=5 grounding=0.58
--------------------------------------------------------------------------------
cases_total: 3
success_rate: 1.000
citation_presence_rate: 1.000
citation_valid_rate: 1.000
avg_source_count: 5.000
avg_grounding_overlap: 0.650
```

## 3. Testing API dengan Postman (Integrasi Backend)

### Kenapa Postman Penting?

Postman bukan hanya alat testing — ia berfungsi sebagai **kontrak API** antara tim RAG dan **backend engineer** yang akan mengintegrasikan sistem ini ke dalam aplikasi produksi (website, mobile app, atau internal tools).

**Workflow Integrasi:**
```
RAG Team                    Backend Engineer
──────────                  ─────────────────
Develop API → Export Postman Collection → Import → Test & Integrate
                    ↓
            Postman Collection = API Contract
```

### Setup Environment

Buat environment baru (misal: `rag-local`) di Postman dengan variabel:

| Variable | Value |
|----------|-------|
| `gateway_base_url` | `http://localhost:8080` |
| `worker_base_url` | `http://localhost:8000` |
| `internal_api_key` | *(INTERNAL_API_KEY Anda)* |

### Endpoint Utama untuk Integrasi

#### A. Chat (Paling Penting untuk Frontend/Backend)

Request dan response shape ini yang akan digunakan backend engineer:

-   **Method:** `POST {{gateway_base_url}}/api/chat`
-   **Body:**
```json
{
  "messages": [
    { "role": "user", "content": "Apa ringkasan dokumen ini?" }
  ]
}
```
-   **Response:**
```json
{
  "response": "Berdasarkan dokumen, ... [S1] [S2]",
  "sources": [
    {
      "id": "S1",
      "filename": "document.pdf",
      "doc_id": "abc123",
      "chunk_id": "...",
      "text": "...potongan teks asli..."
    }
  ]
}
```

#### B. Ingestion (Upload PDF)
-   **Method:** `POST {{gateway_base_url}}/api/ingest`
-   **Body:** `form-data`, Key: `file` (type: File)

#### C. Document Management
| Method | Endpoint | Fungsi |
|--------|----------|--------|
| `GET` | `/api/documents` | List semua dokumen |
| `GET` | `/api/documents/{docId}` | Detail satu dokumen |
| `DELETE` | `/api/documents/{docId}` | Hapus berdasarkan doc_id |
| `DELETE` | `/api/documents/by-filename?filename=X` | Hapus berdasarkan filename |
| `DELETE` | `/api/reset` | Hapus seluruh koleksi |

#### D. Worker Internal (Debug Only)
-   **Method:** `POST {{worker_base_url}}/internal/retrieve-context`
-   **Headers:** `X-Internal-Api-Key: {{internal_api_key}}`
-   Endpoint ini untuk inspeksi raw retrieval tanpa answer generation — biasanya tidak diekspos ke frontend.

Untuk panduan lengkap beserta semua response shape, lihat file `POSTMAN.md` di root project.

## 4. Interpretasi Hasil

### A. Checklist Kualitas RAG

| Metrik | Target | Tindakan Jika Gagal |
|--------|--------|---------------------|
| `success_rate` | 100% | Cek koneksi API Gateway + Worker + Qdrant |
| `citation_presence_rate` | > 90% | LLM prompt perlu lebih ketat, atau Citation Repair tidak berfungsi |
| `citation_valid_rate` | 100% | Bug di CitationValidator atau context building |
| `avg_grounding_overlap` | > 0.5 | Retrieval perlu tuning (alpha, rerank, top-k) |

### B. Debugging Retrieval

Jika `grounding_overlap` rendah:

1.  **Cek HYBRID_ALPHA** (di `worker/app/core/config.py`):
    -   Turunkan untuk prioritaskan keyword matching
    -   Default: `0.3` (30% semantic, 70% keyword)

2.  **Cek cross-encoder reranking:**
    -   Pastikan `RERANK_MIN_SCORE` tidak terlalu tinggi
    -   Default: `0.001`

3.  **Cek diversity filter:**
    -   `MAX_SOURCES_PER_DOC = 2` mungkin terlalu ketat jika hanya 1 dokumen

4.  **Cek document ingestion:**
    ```bash
    # Re-ingest dokumen
    curl -X DELETE http://localhost:8080/api/reset
    # Upload ulang
    curl -X POST http://localhost:8080/api/ingest -F "file=@document.pdf"
    ```

### C. Menambah Test Cases

Untuk proyek produksi, buat file evaluasi custom:

```json
[
    {"id": "exact_match", "question": "Sebutkan judul dokumen secara persis"},
    {"id": "specific_term", "question": "Apa yang dimaksud dengan [istilah teknis]?"},
    {"id": "negative", "question": "Pertanyaan yang jawabannya tidak ada di dokumen"},
    {"id": "complex", "question": "Bandingkan metode A dan B yang disebutkan"},
    {"id": "follow_up", "question": "Jelaskan lebih detail tentang poin terakhir"}
]
```

### D. Penjelasan Grounding Overlap

Fungsi `grounding_overlap()` mengukur seberapa banyak kata dari jawaban yang ditemukan di source text:

-   **Nilai tinggi (0.7-1.0):** Jawaban sangat grounded, kebanyakan kata ada di sumber
-   **Nilai sedang (0.4-0.7):** Jawaban cukup grounded dengan beberapa elaborasi
-   **Nilai rendah (<0.4):** Perlu investigasi, kemungkinan hallucination
